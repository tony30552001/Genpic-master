# 對話創作回覆品質改善計畫

> 文件狀態：規劃中，尚未實作
> 建立日期：2026-10-24
> 範圍：對話創作（`api/image-chats`、`api/_shared/imageChatAgent.js`、`src/components/chat/`）的回覆品質、上下文、回饋與評測

## 1. 背景與依據

對話創作已能一次生成多張圖片並遵守偏好記憶，但回覆品質仍受幾個結構性限制：

1. **AI 看不到圖。** `describeAssistantMessage` 只把每張圖寫成「[已送出生成新圖：<prompt>]」。模型只知道當時要求了什麼，不知道實際畫出什麼。
2. **附圖只交給生圖模型。** 使用者附的參考圖在 `queueImage` 交給生圖模型，`streamResponse` 的訊息只有文字，對話模型本身看不到。
3. **「資訊足夠」沒有定義。** 系統提示詞只說「資訊不足就追問」，因此模型多半直接生圖。
4. **沒有回饋與評測。** 不知道哪一張圖不好、為什麼不好，修改提示詞後也無法證明品質是否變好。

不導入 CopilotKit 這類 agent UI 框架。它處理的是回覆的呈現方式與狀態同步，不會提升回覆品質，而且會取代現有的串流、`llmRuntime` 重試與備援、租戶模型政策。

## 2. 執行順序

| 順序 | 項目 | 依賴 |
| --- | --- | --- |
| 1 | ④ 固定測試題與評測腳本 | — |
| 2 | ① 先確認需求再生圖 | ④（需要基準分數） |
| 3 | ② 讓 AI 知道前幾張圖的實際內容 | ④ |
| 4 | ③ 👍／👎／重來回饋 | ②（回饋要放進同一份上下文） |

先建立評測並記錄基準，之後每一項都用同一組題目比較前後差異。

## 3. ④ 固定測試題與評測

### 題目

- 檔案：`api/evals/imageChat/cases.json`，約 25 題。
- 每題包含：先前的對話歷史（含已生成的圖與描述）、偏好記憶、設定、本輪使用者訊息、預期結果。
- 題型涵蓋：
  - 需求模糊（應追問）
  - 需求完整（應直接生圖）
  - 多張圖（張數要正確，每張描述要能獨立使用）
  - 修改指定版本（應使用 `refine_image`）
  - 「記住…」（應呼叫 `remember_preference`）
  - 與偏好記憶衝突（以本輪明確要求為準）
  - 「直接畫」（不追問）

### 評分

- **規則比對**（程式判斷，穩定、不需額外費用）：
  - 是否呼叫工具、呼叫哪些工具、生成幾張
  - 生圖描述是否包含必要元素，以及不得出現的內容
  - 是否在需要時追問，追問數量不超過上限
  - 是否寫入記憶，記憶內容是否符合預期
- **模型評分**：由另一個模型依評分標準為生圖描述打 1–5 分（完整度、是否遵守記憶、是否保留先前仍有效的要求），並附一句理由。評分模型與受測模型分開設定。

### 執行

- 腳本：`api/scripts/eval-image-chat.cjs`，直接呼叫 `buildSystemMessage`、`buildModelMessages`、`toolsFor`、`streamResponse` 與 `resolveDecision`，不經過 HTTP 與資料庫寫入。
- 使用租戶實際指派的 `image_chat` 模型，每題執行 3 次，以呈現不穩定的題目。
- 結果寫入 `api/evals/imageChat/results/<日期>.json`，並和已提交的 `baseline.json` 比較，列出變好、變差的題目。
- 預設不實際生圖。
- 只在本機手動執行，不放進 CI，因為需要正式環境的模型金鑰，而且會產生費用。

## 4. ① 先確認需求再生圖

### 系統提示詞（`buildSystemMessage`）

- 定義「資訊足夠」：主題、圖上的文字內容（無文字模式除外）、用途三項都清楚。
- 資訊不足時：
  - 用條列整理目前理解的需求
  - 只問缺少的項目，最多兩個問題
  - 不呼叫工具
- 以下情況直接生圖，不追問：
  - 使用者說「直接畫」「先畫看看」
  - 描述已滿足三項條件
  - 修改現有的圖
  - 偏好記憶已補足缺少的項目

### 前端

- 追問的回覆下方顯示快速回覆：「開始生成」「我再補充」。
  - 「開始生成」送出固定訊息，例如「直接畫」，走一般流程。
  - 「我再補充」只把焦點移到輸入框。
- 只有最新一則助理回覆是追問時才顯示快速回覆。
- 判斷依據由後端在訊息上提供，例如 `needsConfirmation`，前端不自行解析文字。

## 5. ② 讓 AI 知道前幾張圖的實際內容

### 圖片描述

- Migration `030`：`image_chat_images` 新增 `description text`。
- 圖片工作成功時，由 worker 在結算流程中用支援看圖的模型產生 2–4 句描述，存入 `description`。
  - 描述的內容：構圖、主體、配色、圖上實際出現的文字，以及和要求不符的地方。
  - 用 `llmRuntime.generateJson()` 呼叫，沿用現有的重試與跨供應商備援。
  - 產生描述失敗不影響圖片本身成功，但要記錄錯誤；上下文改用原本的 prompt，並標示「無描述」。
- `describeAssistantMessage` 改成輸出 `[v3 生成新圖：<prompt>｜實際畫面：<description>]`。

### 使用者的修改意見

- 使用者訊息記錄送出當下選取的版本（`source_job_id`）。
- 上下文改寫成「（針對 v3）標題改大一點」，讓模型知道意見是針對哪一張。
- 版本編號和前端 `versions` 的規則一致。

### 附圖

- `streamResponse` 的訊息內容改成可以同時帶文字和圖片：
  - Azure Responses API 使用 `input_image`。
  - Gemini 使用 `inlineData`。
- 只有本輪的附圖交給對話模型看。歷史中的附圖改用文字描述，以控制費用與延遲。

## 6. ③ 👍／👎／重來

### 資料與 API

- `image_chat_images` 新增：
  - `feedback text`：`up`、`down` 或 `NULL`
  - `feedback_reason text`
  - `feedback_at timestamptz`
- 新增 `PUT /api/image-chats/:chatId/images/:jobId/feedback`：
  - 驗證擁有權與圖片已成功
  - 可以重複設定，也可以清除
- 同步更新 `openapi.js`、`server.js` 與測試。

### 介面

- 每張完成的圖片下方有 👍、👎、重來三個按鈕，各自有 `aria-label` 與 `aria-pressed`。
- 按 👎 後在圖片旁展開原因：文字錯誤、構圖、風格、不符需求、其他（可自行輸入）。可以略過。

### 寫回偏好記憶（AI 提議，使用者確認）

- 回饋與原因放進下一輪的上下文，例如 `[v3 使用者回饋：👎 文字錯誤]`。
- 系統提示詞要求：同類問題出現兩次以上，或使用者的原因明顯是長期偏好時，AI 在回覆中提議「要記住：避免…？」，不直接呼叫 `remember_preference`。
- 前端在提議下方顯示「記住」「不用」。按「記住」才呼叫 `remember_preference`，寫入記憶並顯示「已記住」卡片。
- 提議內容由後端以結構化欄位提供（例如 `memorySuggestion`），不靠前端解析文字。

### 重來（AI 參考回饋改寫）

- 按「重來」會送出一輪新的對話，內容包含原圖版本、原本的描述與回饋原因，由 AI 改寫描述後生成。
- 每次重來都會多一次對話模型呼叫，結果可能和原圖差較多。
- 新圖是一個新版本，原本的版本保留。

## 7. 驗收

- 評測：每一項完成後重新執行 ④，規則比對的通過率不低於基準，模型評分平均不下降，並在 PR 說明附上前後比較。
- 單元測試：
  - 系統提示詞的關鍵規則
  - 上下文的描述與版本標示
  - 回饋 API 的擁有權與輸入驗證
  - 快速回覆與提議記憶的前端互動
- 部署：migration `030` 與後續 schema 變更都要手動套用到正式環境（`node api/scripts/migrate.cjs <檔名>`）。

## 8. 尚待確認

- 「資訊足夠」的三項條件在不同用途（資訊圖表、分鏡、自由畫面）是否需要不同標準，等 ④ 的結果再決定。
- 產生圖片描述的模型要使用哪一個角色指派，以及描述是否要讓使用者看見。
- 評分模型的評分標準需要用 5–10 題人工標註校正，確認和人的判斷一致後才作為驗收依據。
