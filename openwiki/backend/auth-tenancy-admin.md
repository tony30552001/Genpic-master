# Authentication, tenancy, and administration

Protected handlers call `requireAuth`, then conventionally rate-limit and resolve tenant identity. `requireAuth` uses the server session cookie and enforces CSRF for unsafe methods; it returns a normalized provider identity only after the session is live and its user is active. The complete cookie, expiry, and Entra/Google issuance flow is documented in [server sessions and BFF sign-in](sessions.md). `AUTH_DISABLED` creates a local identity only outside production; production detection explicitly ignores it.

`resolveIdentity` obtains or creates the initial tenant and resolves a user by normalized `(tenant_id, email)`. `getDefaultTenant` shares its in-flight/resolved lookup for the process; if that lookup fails, it clears the cached promise so a later request can retry. `getOrCreateUser` first reads the row and returns it without an upsert when its normalized email, display name, and configured-admin role are already current. Otherwise, its upsert refreshes identity fields and can promote a configured `ADMIN_EMAILS` identity to `admin` without demoting an existing role. An inactive record has no usable `userId`; resource handlers conventionally turn that into 401. After that active identity check, `api/auth/index.js::createSessionForIdentity` calls `recordAuthProvider(userId, provider)` before creating the opaque session. It accepts only `entra` and `google`, and the `IS DISTINCT FROM` update avoids a write when the persisted last provider is unchanged. The durable uniqueness, provider, and session-table constraints are in [schema](../data/schema.md). A valid session carries the provider subject, but authorization remains based on the persisted tenant/user record rather than a client-selected identity.

## Administration and policy

`requireAdmin` rejects inactive users and requires role `admin`, except for the true local non-production bypass. `adminService.js` maps `/api/management/users?page&pageSize&search`, `/user-options`, `/history?userId&source&page&pageSize`, `/styles?userId&page&pageSize`, and `/settings`; updates use `PUT /users/:id` or `PUT /settings`, and admin style removal is `DELETE /styles/:id`. User list and user-option records include nullable `authProvider`; it is the last successful `entra` or `google` sign-in, not a provider token or an authorization input. `listUsers` searches display name and email only within the admin tenant. `buildSearchPattern` trims input and escapes `\\`, `%`, and `_`, so these remain literal characters in the PostgreSQL `ILIKE` query; an empty search omits the predicate while pagination continues to apply. The history and styles list records carry `hasImage` and `hasPreview`, rather than embedding URLs. `GET /history-images/:id` and `GET /style-previews/:id` retrieve `{ imageUrl }` only when the requested history/style belongs to the admin tenant, return 404 for a missing/empty asset, and set `Cache-Control: private, max-age=3600`. The API lists only the admin tenant, applies optional `userId` filters to history/styles, clamps page size to 100, validates `admin|editor|viewer` and boolean status, disallows self-disable, and prevents demoting or disabling the final active admin. Unlike normal `/styles/:id`, whose deletion requires creator ownership, management deletion can remove any style in the tenant after nulling history references. The browser's table, page-local image preview, and download presentation consume this availability-plus-image contract; see [administrator panel and history preview](../frontend/admin-panel.md).

`tenant_model_settings` is created lazily by `ensureModelPolicy`. `GET /management/settings` returns `{ modelPolicy, supportedModels }`; `PUT` initializes then validates/persists `{ allowedModels, defaultModel }` with `updatedBy`. `validateModelPolicy` accepts only `gpt-image-2`, requires it to be allowed and selected as default, and rejects removed or unknown renderers. Migration `025_gpt_image_only.sql` changes defaults and normalizes existing rows to that sole policy before deployment. Generation and history use the default, so this setting remains runtime provider policy rather than merely UI presentation; it is not a client-side model-selection surface.

### Tenant analysis models

`api/_shared/llmProviders.js` owns the six-role catalog; `llmModels.js` owns its tenant catalog and assignments. `GET /management/llm-models` returns models without plaintext API keys (`hasApiKey` only), assignments, roles, and provider metadata. Administrators use `POST`, `PUT`, and `DELETE /management/llm-models[/id]`; an empty update key retains the prior encrypted value, duplicate labels are conflicts, and deletion is refused while an assignment references the model. `PUT /management/llm-roles/:role` upserts a primary and optional distinct fallback, both of which must be tenant-local. Provider matching is intentionally not an assignment rule: any role can select Azure OpenAI or Google Gemini models, including a cross-provider fallback. `POST /management/llm-model-tests` tests either an already stored model or draft configuration and returns a success/latency result; it is not a secret-return path.

`resolveRoleModel(tenantId, role)` decrypts only the selected model(s) for server-side calls. `llmRuntime.js::generateJson` then dispatches each attempt by the active model's provider, so roles such as `document_analysis`, `prompt_optimization`, `deck_authoring`, `style_analysis`, `filename`, and `scene_optimization` no longer have a provider pairing. The management connection test uses this same runtime boundary, including its output-truncation handling, rather than calling a provider adapter directly. Azure endpoints must be public HTTPS URLs; Gemini endpoint input is discarded because its SDK owns the endpoint. A missing assignment is `LlmConfigurationError` (`503 llm_not_configured`), not a fallback to environment configuration. The model tables and encryption boundary are documented in [schema](../data/schema.md), and runtime callers/retry behavior are documented in [AI generation](ai-generation.md).

`/api/me` is the browser profile boundary and returns `{ user: { id, email, displayName, role }, modelPolicy }`; `AuthProvider` folds it into `profile` and `isAdmin`. See [browser application and authentication](../frontend/application.md) for the profile-load and gate lifecycle.

## Change and validation guide

Consult this page for identity resolution, authentication-provider recording, authorization predicates, user status/roles, tenant query filters, `/api/me`, management image retrieval, user search, or model-policy changes. Preserve ordering: authenticate the session first, then rate-limit and resolve persisted identity before operating on tenant data; record the provider only after the identity is active and before session creation. For identity changes, preserve normalized-email lookup, no-write behavior for an unchanged row or provider, configured-admin promotion without ordinary-role demotion, and retry after a default-tenant lookup failure. For user search, keep the tenant predicate in both count and list queries and escape pattern metacharacters rather than treating caller input as a pattern. A new protected mutating route also needs the session/CSRF contract and the synchronized public declaration described in [HTTP API](http-api.md).

Run `api/_shared/__tests__/auth.test.js` for missing-session, CSRF rejection, and valid-session behavior; run `api/_shared/__tests__/identity.test.js` for unchanged-row, tenant-cache, accepted-provider, and no-op recording behavior. `api/admin/__tests__/adminResources.test.js` is the focused handler check for URL-free history list records, tenant-scoped image/preview queries, cache header, missing-resource responses, user-search wildcard escaping, and provider fields in user/options results. When changing session mechanics, add `session.test.js` from [server sessions](sessions.md). Run `src/services/__tests__/adminService.test.js` for browser URL/payload integration when it exists. Authorization predicate changes still require authenticated same-tenant and cross-tenant negative checks, and model-policy changes should additionally exercise the generation owner described in [AI generation](ai-generation.md).
